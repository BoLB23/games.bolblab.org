# Security review — 2026-09-04

Scope: [issue #4](https://github.com/BoLB23/games.bolblab.org/issues/4), the open
authentication/deployment concerns, and [PR #1](https://github.com/BoLB23/games.bolblab.org/pull/1)
(pytest discovery). The working tree was reviewed after the local changes were
integrated; no GitHub issue or PR comments were posted.

## Completed locally

- Production settings reject development authentication and development auth
  rejects non-loopback browser origins.
- OIDC authorization state is bound to a short lived HttpOnly transaction
  cookie, consumed atomically, and cleared on callback success or failure.
- OIDC discovery and token responses validate their JSON shape before use.
- Credentialed CORS uses exact origins, including Milton Estates. The
  multiplayer socket additionally checks the configured game origin.
- Root and mounted API docs, ReDoc, and OpenAPI are disabled in production;
  validation errors are JSON encoded consistently.
- The default Kubernetes API deployment uses production OIDC, secure cookies,
  HTTPS origins, production seeding, and TLS redirect. Local development uses
  the explicit `k8s/overlays/development` overlay.
- Actions are pinned to verified commit SHAs. SDK publication verifies the tag
  commit is on `origin/main` and requires `sdk-release`; image publication is
  gated by `production-images` on main pushes.
- PR #1's pytest discovery fix is incorporated as `pythonpath = ["."]`.

The broader review also covered the API data layer, SDK, catalog, Flappy Mike,
and multiplayer changes. Those changes add database locking and SQL-backed
ranking safeguards, conditional save deletion, retry/dead-letter and storage
handling, durable account-aware Flappy best scores, logout/query/PWA fixes, and
session/multiplayer race protections.

## Remaining architecture and operations

Browser origin checks are a browser transport boundary, not game authority.
Authenticated non-browser clients can still call game APIs, and score/session
requests are authorized to the platform user rather than a cryptographic
per-game capability. The server has no authoritative game simulation or
anti-cheat evidence model, so leaderboard values remain trust-based within the
documented bounds. Closing this requires a per-game capability/token protocol,
server-side score verification, and a game-specific authoritative service.

The production manifests still require operators to create the TLS secret and
the OIDC `games-secrets` values, and apply the Google OIDC ConfigMap. The
`production-images` environment is restricted to `main`; `sdk-release` is
restricted to `sdk-v*` tags. The active tag ruleset (ID 22302173) prohibits
updating or deleting `sdk-v*` tags. No required environment reviewers are
configured. Main branch protection is prepared and pending the final push.
No live deployment was performed.

Issue #4 remains open for the per-game capability and authoritative score
architecture described above. PR #1's code is integrated; no issue or PR
comments were posted.
